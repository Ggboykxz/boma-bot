# Wave 1 #008 — apps/desktop/src/stack.ts — Reliability (v0.4.0)

Scope: read-only review of `apps/desktop/src/stack.ts` (before-m5, 451 lines). v0.4.0 proposal for the reliability lens, aimed at the failure modes seen in v0.3.0-rc (Windows first-launch migrate failures) plus boot timeout, PG port collision and orphaned children. No code edits.

## Failure modes observed / credible

1. **No timeout anywhere in bring-up.** `run()` (206-230) has no deadline; a hung `initdb`, `pg_ctl -w start`, or `boma migrate` wedges `startStack` forever — no dialog, no `fatal`, the app simply never loads the window. The only bound is `waitForHealth` (90 × 1 s ≈ 90 s), and even that ignores early child death (polls on after `serve` already exited).
2. **`serve`/`worker` spawns have no `error` handler.** Unlike `run()`, the raw `spawn` calls at 369/378 (and the worker retry at 390) attach no `error` listener. A missing `boma.exe` / missing DLL on Windows emits `error` on the ChildProcess with no listener → uncaught exception → the desktop process dies instead of showing the failure dialog. `serve.pid ?? ""` is then written to the pid file, leaving a corrupt artifact.
3. **PG port collision (TOCTOU + orphans).** `pickFreePort()` (99-115) closes its probe socket before `postgres` binds — classic race. The chosen `pgPort` is not persisted, not verified with `pg_isready`; `pg_ctl` exit 0 is trusted blindly. `reapOrphans` (193-203) only reaps `serve`/`worker` pid files — **never postgres itself**. An unclean exit leaves a postmaster alive holding `pgdata`; next launch picks a *new* random port, `pg_ctl -D pgData start` then fails on the stale `postmaster.pid` ("lock file exists"), and the user is bricked at the `postgres` step until they manually delete `boma/`. The httpPort TOCTOU at 317-321 is the same shape (probe, then `serve` binds later).
4. **Orphan kill is indiscriminate and not tree-aware.** `terminatePid` (164-190) sends SIGTERM→SIGKILL to whatever pid the file holds — no check that it is actually our `serve`/`worker` (pid reuse kills an innocent process), no process-group/tree kill (`boma serve` children leak), EPERM is treated as "gone" (live orphan skipped silently). `stopStackAt` (422-435) never verifies postgres actually stopped; a wedged postmaster keeps `pgdata` locked and the next boot hits mode 3.
5. **Failed migrations on first Windows launch (v0.3.0-rc) — root cause not yet proven (GUESS):** (a) missing DLL / unsigned binary blocked or delayed by Defender on first run — the code already hints this in the empty-output branch (361-363) but never *preflights* the binary, and the first scan delay can outlast any implicit budget; (b) Defender/AV file lock while `boma.exe` is freshly extracted → partial read, `migrate` exits non-zero with empty output; (c) a prior failed `migrate` left a half-migrated schema; re-run may be fine if migrations are idempotent (unverified) — nothing in the log says whether they are. What *is* certain: on migrate failure the stack is torn down, pg stopped, but there is no bounded retry, no binary preflight, no automatic recovery, and the dialog demands manual surgery (`delete boma/`).
6. **Initdb partial-cluster brick.** Detected correctly (289-294) but the only remedy is manual deletion of `boma/` — acceptable for a dev build, not for v0.4.0 first-run UX.
7. **Worker supervision fragilities.** `workerCrashes` (402) is declared *after* the closure that uses it (works, but brittle); the retry spawn loses `stdout` piping; no backoff; the cap emits `fatal` but leaves the pid file stale; a retry `spawn` failure hits mode 2 again.
8. **Log-tail and size hazards.** `logTail` (131-139) reads the whole log into memory; `boma.log`/`postgres.log` are never rotated; failure detail omits `pgPort`/`httpPort`/binary path — support cannot reproduce.
9. **Small honesty gaps.** `stopStack` takes an unused `httpPort=0`; pid files written non-atomically; `persistPort` not atomic (crash mid-write → garbage port, handled on read but noisy); `stopStackAt` swallows pg-stop failure entirely.

## Proposals (concrete changes for v0.4.0)

**H1. Bounded bring-up.** Add `timeoutMs` to `run()` (default 120 s; 60 s for `pg_ctl stop`); on timeout SIGTERM → 5 s → SIGKILL, resolve `{ code: -1, output: "…timed out after <n>ms" }` and let the step throw `StackError` with the step name. Wrap `startStack` body in an overall 180 s budget (first-boot generous for AV scans); on expiry, stop what started and throw `StackError("healthy", "bring-up exceeded …")`. No `run()` may hang forever.
**H2. Early-death health probe.** In `waitForHealth`, race each probe with a `serveExited` promise (already have the `exit` event); resolve `false` immediately on exit, and carry the exit code/log tail into the `healthy` StackError instead of polling 90 s.
**H3. Preflight binaries.** Before any spawn: `existsSync` + size>0 (+ on Windows, PE magic `MZ` and machine-type check for x64 vs arm64 mismatch) for `initdb`, `pg_ctl`, `boma`. On failure throw `StackError` naming the missing/unreadable file and `BOMA_STACK_RESOURCES` — this is the likeliest v0.3.0-rc empty-output migrate case. Cheap, no behavior change on healthy systems.
**H4. Fix the PG lifecycle end-to-end.** (a) `reapOrphans` also reads `<pgData>/postmaster.pid`; if the pid is alive **and** its command line matches our `pgdata` path, stop it via `pg_ctl -D pgData stop -m fast` *before* port selection; if stale, delete `postmaster.pid` only after confirming the pid is dead or not a postgres on our data dir. (b) After `pg_ctl` returns 0, poll `pg_isready -p <pgPort>` (or a 127.0.0.1 TCP connect + `SELECT 1` via a tiny probe) up to 15 s; non-ready → treat as `postgres`-step failure with log tail. (c) On bind-race failure, retry the whole PG sub-flow once with a fresh port. (d) Persist `pgPort` to `<root>/pg.port` for support; delete on clean stop.
**H5. Safe, tree-aware kill.** Verify the pid's command line contains our binary names before SIGTERM (`ps -p <pid> -o command=` on POSIX; `Get-CimInstance Win32_Process`/`tasklist /v` on Windows); kill the process **group** on POSIX (`process.kill(-pid)` after `detached:true` for children we spawn) and `taskkill /PID <pid> /T /F` on Windows. Distinguish ESRCH (gone) from EPERM (log + skip). Keep 3 s grace + SIGKILL fallback, add an overall 8 s per-pid deadline.
**H6. First-Windows-launch migrate path.** Preflight (H3) + one bounded migrate retry (2 s apart, only on non-zero/empty-output, logged as `migrate retry 1/1`). If the retry fails, `stopStackAt` as today, and the StackError detail includes: exit code, binary path, `BOMA_DATABASE_URL` host:port, last 20 log lines, and a `BOMA_STACK_RESET=1` instruction that moves `boma/` aside to `boma.broken-<timestamp>/` and re-runs first-boot cleanly (move, never delete). Verify with the boma CLI whether migrations run in a transaction; if not, recommend `migrate --single-transaction` (or equivalent) — half-applied first-boot migrations are the worst v0.3.0-rc outcome. Marked GUESS until confirmed against the binary.
**H7. No unhandled child errors.** Attach `error` handlers to `serve`, `worker`, and the retry spawn: on `error`, if not yet healthy → tear down and throw/emit `StackError("serve"|"worker", …)`; after healthy, emit `fatal` (current contract). Pipe the retry's `stdout` too; declare `workerCrashes` before the closure; exponential backoff (0.5 s, 2 s) and reset the counter on a worker that stays up ≥ 60 s.
**H8. Honest, bounded logs and stop.** `logTail`: stat first, read only the last 64 KiB, cap at 12 lines. Rotate `boma.log`/`postgres.log` at 512 KiB → `.1` in `openServerLog` and before pg_ctl start. Failure details always include `platform`, `pgPort`, `httpPort`, binary path. `stopStackAt` gains an overall 10 s deadline, verifies postgres absence afterward (retry SIGKILL on postmaster.pid if still alive), and writes pid files atomically (`tmp` + `rename`, `0600`). `stopStack` drops the dead `httpPort` parameter (or wires it honestly).
**H9. StackError taxonomy.** Add `cause` and a stable `code` (e.g. `BOMA_STACK_PG_PORT_BUSY`, `BOMA_STACK_MIGRATE_EMPTY_EXIT`) so the dialog and support can branch without string-matching.

## Verification plan

- **Fault-injection shims.** Build a fake `BOMA_STACK_RESOURCES` tree (shell/`.cmd` shims, Windows via `.exe` wrappers): `initdb` sleeps forever (assert H1 kill, dialog ≤ deadline); `boma migrate` exits 1 with empty output and with output (assert H3/H6 message contents, pg stopped, pid files removed, `boma.log` has `fatal: migrate:` line); `postgres` binds the probed port first (assert H4 retry-once); fake `serve` never binds (assert H2 immediate `healthy` failure); fake postgres left running in pgdata from "previous crash" (assert H4 adopt/stop, exactly one postmaster afterwards).
- **Orphan suite.** Start stack, `SIGKILL` the desktop process, relaunch: assert one postmaster, port file consistency, no foreign pid killed (pid file pointed at the test runner itself must NOT be signalled — H5 cmdline guard).
- **Windows clean-VM rehearsal.** Fresh userData, Defender on, path with spaces + non-ASCII, OneDrive-redirected `%APPDATA%`, simulated AV quarantine of `boma.exe`. Assert: dialog (not crash) within budget; `BOMA_STACK_RESET=1` moves state aside and boots.
- **Stop path.** `stopStack` on a wedged postgres (shim ignores fast-stop): returns ≤ 10 s, postmaster dead or SIGKILLed, pid files gone.
- **Health/retry.** Worker killed twice → `fatal` emitted once, pid file consistent; transient single kill → retried worker healthy, stdout visible in `boma.log`.
- **Regression.** Existing bring-up happy path and `ReapOrphans` unit tests (port-file parse, `pidOf` garbage, atomic rename) must stay green.

## Risks / non-goals

- Auto-stopping an orphan postgres could kill an external process that shares `pgdata` — mitigated by cmdline-match + `postmaster.pid` verification (H4/H5); never kill by port.
- One migrate retry can mask a deterministic failure — logged, capped at 1, and the reset path is opt-in.
- `postmaster.pid` parsing is version-sensitive (GUESS); prefer `pg_isready` + cmdline checks over parsing where possible.
- Longer first-boot budget may look like a hang on truly broken machines — surface elapsed-time checkpoints in the dialog.
- Windows process-group semantics differ; `taskkill /T` relies on the tree being ours (spawned by us) — acceptable.
- Non-goals: sandboxing, navigation guard, updater, dialog UX copy (see main.ts proposal #006), and any spec behavior changes — none proposed here.
- All items are desktop-stack only; backend crates untouched.
