# Wave 1 #010 — apps/web/app/admin/plugins/page.tsx — Reliability (v0.4.0)

Scope: read-only review of `apps/web/app/admin/plugins/page.tsx` (before-m5, 12 lines — a thin wrapper rendering `components/admin/plugins-screen.tsx`). Reliability surface lives in `PluginsScreen` (168 lines), `lib/api/rpc.ts` (`call`, `adminPluginsList`, `adminPluginsDecide`) and the Rust side (`admin_plugins_decide` / `decide_submission`). v0.4.0 proposal. No code edits here. Line numbers cite the before-m5 worktree.

## Failure modes observed / credible

1. **Decision race on shared `deciding` state.** `deciding` is a single `string | null` (plugins-screen.tsx:31,62-76). Approve/reject submission A, then decide B before A settles: B sets `deciding = B`; when A finishes, `finally` sets `deciding = null`, re-enabling B's buttons mid-flight. A second click on B fires a duplicate decide → server answers `Conflict` → user sees a generic failure on an action that actually succeeded. Same window exists for double-clicking B before React re-renders the disabled state.
2. **Submit-review race between concurrent admins.** Two admins (or two tabs) see the same pending row. Server is safe at the SQL level (`UPDATE ... SET status = $2 WHERE id = $1 AND status = 'pending'`, admin.rs:274-312, returns `Conflict` on 0 rows), but the UI cannot distinguish "already decided by someone else" from "network/500 failure": every catch path shows the same `t("admin.plugins.error")` (plugins-screen.tsx:69-71). After a conflict the row stays visible with a misleading error and no way to refresh (see 3).
3. **Stale list with no refresh affordance.** List loads once on mount / `reloadToken` (plugins-screen.tsx:39-60). There is no poll, no refetch-on-focus, no manual refresh button in the ready state; `reload()` is only reachable from the error state (118-121). `admin.plugins.list` accepts a `status` filter but the screen hardcodes `pending` (41) and server caps at `limit = 200` (usecases.rs, `admin_plugins_list`) with no pagination or overflow indicator — a backlog >200 is silently truncated, and `unconfirmed` submissions never appear at all.
4. **`Conflict` vs real failure swallowed.** `decide`'s catch ignores the error entirely (69-71). `RpcError` carries `code` and `status`; `FORBIDDEN` → queue access lost (role revoked mid-session), `Conflict` → stale row, anything else → genuine fault. All three collapse to one message; the list is not reloaded, so the admin cannot recover without a full page reload (and there is no button for it).
5. **No deadline on any request.** `call()` issues `fetch` with no timeout (rpc.ts:245-272). A hung list request leaves the skeleton forever (phase stays `loading`, no error, no retry). A hung `decide` leaves the button disabled forever (`finally` never runs). `AbortController` covers unmount/list-reload only; `decide` passes no signal.
6. **Optimistic removal without reconciliation.** On success the row is filtered out locally (68) — correct given the atomic server transition, but a successful decide whose audit append fails is invisible (`let _ =` in `admin_plugins_decide`, usecases.rs — decision persists, audit line lost, UI reports success). Conversely, a `decide` that times out client-side may have committed server-side; the UI keeps showing the row, and the next click yields `Conflict` with a false "error" message.
7. **Loading/error semantics gaps.** Reload flips `phase` to `loading` and unmounts the whole list (skeleton flash, focus loss). `forbidden` phase (107-112) offers no recovery path even though new grants can make access valid without a reload. The `loading` skeletons are `aria-hidden` with no `aria-busy`/`role="status"` on the region, and the raw server `status` string (134) is rendered unlocalized. `createdAt` is received but never shown, so admins cannot age staleness.
8. **Invalid submissions are display-safe but decision-blind.** Source is rendered as text in `<code dir="auto">` (133) — good, never executed or injected. But there is no pre-decision surface for parse/validation detail (ref, subdir, size, duplicate-of-installed); the reviewer approves blind. `name ?? source` (132) can truncate badly for very long names (no `break-words` on the name span).

## Proposals (concrete hardening / error states)

**P1. Per-submission pending state.** Replace `deciding: string | null` with `pendingIds: Set<string>` updated in `decide` entry/`finally`. Disables exactly the in-flight row's two buttons; concurrent decisions on different rows proceed independently; double-click window closed because state is set synchronously before the first await. *Risk:* none material; cleanup on unmount needs an `AbortController` per call or a mounted ref to avoid set-state-after-unmount noise.

**P2. Typed decide errors + reconciliation.** In `catch`, branch on `RpcError.code`/`status`: `Conflict` → drop the row locally and show a neutral "already decided — refreshed" notice, then trigger one `reloadToken` bump; `FORBIDDEN` → flip `phase` to `forbidden`; `Rule`/validation → surface server message verbatim (safe: server strings, no internals); otherwise → generic error. *Risk:* server messages may contain admin-shorthand; confirm they are safe to show (current `Rule` strings are, they are fixed text). Refresh-on-conflict costs one extra list call — bounded, fine.

**P3. Freshness controls.** Add a manual "Refresh" button in the ready-state header (`RiRefreshLine`, existing icon) that bumps `reloadToken` without unmounting the list (keep `phase` as-is during background refetch; only first load uses full skeleton). Optional: `visibilitychange` refetch when the tab regains focus, and a 30-60s poll while `phase === "ready" && document.visibilityState === "visible"`. *Risk:* poll widens the stale-decision window but increases list traffic 1×/min/admin; gate poll behind a visible tab and keep interval ≥30s. Flicker: keep current list rendered during refetch.

**P4. Deadlines everywhere.** Wrap `adminPluginsList` and `adminPluginsDecide` in `AbortSignal.timeout(10_000)` (composed with the existing unmount controller via `AbortSignal.any` if available, else a manual link). On timeout: list → `phase = "error"` with retry; decide → typed error path (P2), which auto-reconciles the row if it actually committed. *Risk:* a 10s decide timeout on a slow but healthy server produces a Conflict-on-retry that the P2 path now handles gracefully — acceptable and self-healing.

**P5. Surface the backlog and the unconfirmed queue.** Show a count header ("N pending") and, when `submissions.length === 200`, render "showing first 200 — refine or export" rather than silent truncation. Consider a status toggle `pending | unconfirmed` if the spec (REQ-058 / §8.7) intends unconfirmed to be reviewable; otherwise document why it is hidden. Add `createdAt` (localized, `Intl.DateTimeFormat`) to each row so age is visible. *Risk:* count display is derived from the capped page, not a server total — label it "oldest shown / cap reached" or add a `total` to the list reply (contract change; flag as DEVIATION if pursued).

**P6. Decision-review affordance (no execution, stay in scope).** Before approve/reject, expand a read-only detail: parsed ref/subdir, source host, submission age, and any duplicate-of-installed marker the backend can cheaply compute (exact canonical-ref match). Never render the submitted code as HTML; keep `<code dir="auto">` text-only. *Risk:* scope creep — detail endpoint may not exist; if absent, defer to a later wave rather than hand-roll parsing in the client. This is a UX-reliability improvement, not new behavior.

**P7. Audit-append visibility.** Surface (log-level or a subtle banner, not blocking) when the decision committed but the audit append was dropped — requires the backend to return `{ status, audited: bool }` or a warning code. *Risk:* response-shape change = contract/DEVIATION; minimally, note the gap in STATE.md instead of shipping silently. Do not block approve on audit.

**P8. Loading a11y.** Wrap the list region in `aria-busy={phase === "loading"}` + `role="status"` with visually-hidden "Loading submissions…"; keep skeletons `aria-hidden`. Localize the raw `status` badge or render it via the i18n layer. *Risk:* none.

## Verification plan

- Playwright: two admin contexts decide the same row concurrently → loser sees "already decided", row disappears, no false error banner; double-click approve fires exactly one RPC (assert via request count).
- Network hang (offline/throttle): list → error+retry within ~10s; decide → typed timeout path, row reconciles after refetch.
- Conflict path: seed decide via second tab; first tab's next decide → row removed via P2 reconciliation, zero unhandled rejections in console.
- a11y: axe on `/admin/plugins` (loading, ready, error, forbidden states); keyboard-only approve/reject; 360px width.

## Risks / non-goals

- No change to the atomic server decide (already correct), no client-side "optimistic approve", no auto-install — review never executes anything.
- Poll/refetch must not clobber an in-flight decide's row removal; reconcile by id, not by blind `setSubmissions(reply)`.
- No new dependencies; all proposals ride existing `RpcError`, BoardUI tokens, `Ri*` icons.
- DEVIATION flags: list-reply `total` (P5) and decide `audited` (P7) are wire-shape changes — require spec/PARITY.md approval before shipping; everything else is internal to the screen + `lib/api/rpc.ts`.
