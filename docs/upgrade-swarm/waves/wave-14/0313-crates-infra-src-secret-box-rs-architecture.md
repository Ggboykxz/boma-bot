# Worker #313 — `crates/infra/src/secret_box.rs` — LENS: architecture — v0.4.0 proposal

- **Status:** PROPOSAL (read-only review; no source changed). CONFIRMED = verified by reading files in this worktree; GUESS = needs test/oracle or load evidence.
- **Scope:** the encryption-at-rest primitive layer for REQ-046 / DEC-10 (ADR-020): envelope encryption with a per-space DEK wrapped under `BOMA_MASTER_KEY`, plus the `space_keys` table and the stores that call this module.

## Summary (current structure, CONFIRMED)

`SecretBox` is a `[u8; 32]` master key plus a `stable` flag. It offers six static operations: seal/open a secret under a caller-owned DEK and wrap/unwrap a DEK under the master key, all AES-256-GCM with a fresh random 12-byte nonce per operation. The persisted unit is the `app` port `SealedSecret { ciphertext, nonce }` — no version, key id, algorithm tag or associated data. The module is correct as a primitive (nonces differ, tamper is rejected, rotated key still reads old ciphertext — tests at lines 208–305), but it is a *primitive*, not a key-management architecture: DEC-10 recommends pluggable KMS (option b) with option (a) as the self-hosted default, and there is no provider seam to plug anything into.

## Architectural findings

- **A1 (HIGH, CONFIRMED):** no self-describing ciphertext. `SealedSecret` is two byte vectors; wrapping and sealing use the indistinguishable same primitive. There is no version, key id or AAD, so (i) a wrapped DEK from space A could be transplanted into space B if RLS were ever misconfigured, (ii) a wrapping blob could be fed to the secret-open path, and (iii) no format migration (new AAD, new KDF, new algorithm) can be rolled out incrementally — every row is unlabeled. Rotation must rewrite all DEKs in one big bang.
- **A2 (HIGH, CONFIRMED):** the master key is never fail-checked in production. `from_env` silently generates an ephemeral key when `BOMA_MASTER_KEY` is absent (lines 56–61); `secrets_vault()` in `crates/bin/src/commands.rs:110` calls it with no gate. `stable_key()` is consulted only by the `rekey` command (line 387). A deployment missing the variable boots, logs one warning, writes secrets it can never reopen after restart, and fails only at the next read. Tests depend on this convenience (`SecretBox::ephemeral()` in dozens of store tests), so a gate must be explicit and configurable.
- **A3 (HIGH, CONFIRMED):** DEK lifecycle is duplicated four ways. `space_keys.rs::load_or_create_dek`, `stores/messaging.rs::unwrap_or_fresh_in` (line 578), `stores/secrets.rs::space_dek` and `stores/destinations.rs` each issue their own `SELECT wrapped_key, nonce … ON CONFLICT DO NOTHING` dance. The header of `space_keys.rs` even admits "the secrets store has its own inline copy kept stable for the recorded path". Four copies of a security-critical race/idempotency rule will drift.
- **A4 (MED, CONFIRMED):** no KMS/HSM seam and no multi-key rotation window. `wrap_data_key`/`unwrap_data_key` are hard-wired to one master key; `rekey` unwraps every row with the old key then rewraps with the new one. There is no key id, so at most one master key can be active; a mid-run failure leaves the table partially rewrapped with no marker of which rows moved. DEC-10 option (b) is structurally unreachable without a trait.
- **A5 (MED, CONFIRMED):** secret material and errors are under-typed. The master key and DEKs are plain `[u8; 32]` values (cloned freely; only `Debug` is custom-safe, lines 30–37), not `secrecy::Secret`/zeroizing containers, contrary to the AGENTS.md "secrets wrapped in secrecy" rule. Every crypto failure — bad nonce length, GCM authentication failure, wrong key, invalid UTF-8, cipher init — collapses to `AppError::Unavailable` (lines 93–114, 131–133, 150), so an operator cannot distinguish tampering, a key mismatch, or a format that needs migration. `fresh_data_key` suppresses `clippy::expect_used` with a bare allow (line 162) rather than returning `Result`.

## Concrete upgrades (v0.4.0)

1. **P0 — versioned, domain-separated envelope.** Replace the bare `SealedSecret` at rest with a `SealedEnvelope { version: u8, key_id: [u8; 16], purpose: Wrap|Secret, ciphertext, nonce }` and feed `(version ‖ key_id ‖ purpose ‖ space_id)` to AES-GCM as AAD. Keep read support for legacy v0 blobs behind a one-way `open_legacy` used only in the migration path, then rewrite rows store by store. *Risks:* this is a persisted-format change → DEVIATION entry in `docs/PARITY.md` and operator approval before shipping; dual-read logic doubles the test matrix; getting AAD wrong on the first write can make data unreadable, so land it test-first with a golden round-trip and a legacy-read test.

2. **P0 — fail fast instead of silent ephemeral keys.** Add a typed startup check: in non-test builds, `build_app` must see `stable_key() == true` unless an explicit `BOMA_ALLOW_EPHEMERAL_KEY=1` dev override is set, validated in the config struct with a clear message. Keep `ephemeral()` for tests. *Risks:* local/CI setups that never set the key will stop booting (many existing tests use `SecretBox::ephemeral()` and must be marked as dev contexts); this is an externally visible behaviour change for anyone running keyless — document as DEVIATION and ship `.env.example` with a generation command.

3. **P1 — one DEK owner.** Extract all `space_keys` access into a single `SpaceKeyStore`/`DekManager` in `infra` (`load_or_create`, `unwrap`, `rewrap`); make `secret_box.rs` own only primitives and have secrets/messaging/destinations/connectors call the manager. Delete the inline copies. *Risks:* touches four stores and the "recorded path" noted in `space_keys.rs`; must preserve the `ON CONFLICT DO NOTHING` survivor semantics and RLS behaviour exactly, or a concurrent first-write can seal a secret under a DEK that is later replaced — cover with a concurrency proptest/integration test against Postgres.

4. **P1 — master-key provider trait for DEC-10(b).** Introduce a `MasterKeyProvider` trait (`wrap`/`unwrap` returning key-id-tagged blobs) with the current env key as `EnvMasterKeyProvider`; stores depend on the trait, not the concrete struct. Add a rotation window where the new key is added first, old key retained for reads, and only then old DEKs rewrapped. *Risks:* broad signature churn across `SecretBox` callers; a real KMS adds network latency and a new availability/failure mode (needs timeouts and graceful degradation), so keep the default provider in-process and identical; don't add an external KMS dependency in v0.4.0 without an ADR.

5. **P2 — typed crypto errors and secret-typed, zeroizing keys.** Wrap key material in `secrecy::Secret<[u8; 32]>` (zeroize on drop), define a `thiserror` `CryptoError` (AuthenticationFailed, BadNonce, WrongKey, InvalidUtf8, KeyUnavailable), replace blanket `Unavailable`, and remove the `expect_used` allow by making `fresh_data_key` fallible. Map `CryptoError` to the generic stable API error at the HTTP boundary only — never leak detail to clients. *Risks:* signature changes ripple into stores and tests; error text must not reach logs/exports with secret hints; zeroization costs a negligible drop-time memset; confirm `secrecy`/`zeroize` versions via `cargo add` and docs.rs, not memory.

## Cross-cutting risks / notes

- Items 1 and 4 are schema/format changes: land behind feature-free dual-read paths, with `docs/PARITY.md` DEVIATION entries and approval before shipping (AGENTS.md: externally visible data-format changes need sign-off).
- GUESS (needs measurement): current nonce generation is random per seal; at realistic secret volumes the 2^96 GCM nonce space is safe, but a per-DEK counter would remove birthday-bound concerns — verify volume before changing, since a counter needs durable state.
- No claim of passing tests is made here; all findings are from source reading in this worktree (CONFIRMED) except where marked GUESS.
