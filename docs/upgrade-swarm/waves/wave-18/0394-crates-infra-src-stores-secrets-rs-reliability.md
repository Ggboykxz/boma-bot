## Current structure (CONFIRMED)

- `PostgresSecretStore { pool, secrets }` implements `SecretStore::{put,list,delete,reveal}`; each method runs inside `tenant::with_tenant`, a transaction that sets transaction-scoped `boma.space_id` / `boma.system_reason` (`tenant.rs:51-143`).
- Envelope encryption: `space_keys` holds one AES-256-GCM-wrapped DEK per space under `BOMA_MASTER_KEY`; `bot_secrets` holds values sealed under that DEK. `SecretBox` never logs its key; `list` answers names/timestamps only (REQ-046).
- `put` resolves the bot's `space_id` via a scoped subquery, mints a DEK on missing row (`INSERT ... ON CONFLICT DO NOTHING` + survivor re-read), then upserts `(space_id, bot_id, name)` including `created_at = EXCLUDED.created_at`.
- `list`/`delete`/`reveal` all anchor `space_id = (SELECT space_id FROM bots WHERE id = $1)`; `reveal` JOINs `space_keys` on `space_id` and returns `Option<SecretString>` to the shell-out executor only.
- `space_dek` (crate-internal, shared with destinations, REQ-065) reads/mints the DEK on a **raw pooled connection** (`pool.acquire()`), outside any tenant transaction.
- `rekey_space_keys` runs under the system tenant, `SELECT ... FOR UPDATE` on every `space_keys` row, unwraps with `old`, rewraps with `new`, sets `rotated_at`; the CLI refuses an ephemeral `old` key. Ciphertexts are untouched (DEC-10).
- All crypto failures in `secret_box.rs` (bad nonce length, AEAD failure, wrong unwrapped key length, invalid UTF-8) map to `AppError::Unavailable`, whose `is_retryable()` is `true` (`app/src/error.rs:49-51`). DB errors map to the same variant via `tenant::unavailable` (warn log).

## Failure modes

1. **Key loss / wrong key.** The master key is env-only; an absent key silently degrades to a per-process ephemeral key (warn only), so a misconfigured prod deployment can seal secrets nobody can read after a restart. A *wrong but well-formed* 64-hex key passes startup validation and fails only at the first `put`/`reveal`, as `Unavailable`. Losing the key loses every secret; ADR-020 explicitly declines backups. No startup canary or key fingerprint catches the mismatch before the first real secret.
2. **Cross-space leakage / DEK isolation.** RLS on both tables plus subquery anchoring look sound for the four port methods. `space_dek` is the gap: it acquires a separate pooled connection where `boma.space_id` is unset and `boma.system_reason` is empty, so `boma.current_space_id()` = `''` and `boma.is_system()` = `false`. Under `FORCE ROW LEVEL SECURITY` (both tables) its `SELECT`/`INSERT` on `space_keys` are not scoped to the caller's space — they either error or, on a role that bypasses RLS, run unscoped (CONFIRMED code fact; which branch occurs in a given deployment is GUESS until tested). The DEK is also minted outside the caller's transaction, so a destination write can commit while its DEK insert rolls back, or vice versa.
3. **Rotation.** `rekey_space_keys` holds `FOR UPDATE` on every space key for the whole loop; one bad row aborts the batch (the transaction rolls back — good) but reports no progress or offending `space_id`. It is not idempotent: re-running with the same old key fails on already-rewrapped rows instead of skipping them. It is offline-only with no overlap protocol: if the app is restarted with the new `BOMA_MASTER_KEY` before rekey finishes, new DEKs get wrapped under the new key and `old.unwrap_data_key` then fails on those rows, wedging rotation. No post-rotation verification step confirms a secret still opens.
4. **Decryption errors / observability.** Corrupt ciphertext, tampered nonce, truncated wrapped key, invalid UTF-8 and a DB outage are all `Unavailable`; routines may retry a permanently undecryptable secret with backoff (REQ-024) and burn their failure budget. No tracing or metric sits at the `reveal` failure site, so silent data-integrity loss is invisible. `reveal` cannot distinguish "no row" (`Ok(None)`) from "row present but unreadable" (`Err`) beyond that one code. Unvalidated `bytea` columns admit malformed rows that only fail at reveal.

## Concrete hardening (with risks)

1. **Startup key canary + fingerprint.** At startup, seal and immediately open a fixed probe under the configured master key; log a non-secret short fingerprint (e.g. first 8 hex of an HMAC of the key) and refuse to serve with an ephemeral key when an env key was expected. *Risk:* a fingerprint could be mistaken for a usable key identifier; it is public by design. *Mitigation:* derive it via HMAC with a domain label, never the raw key; keep the probe in-process (no DB write); make "ephemeral in production" a hard `Config` check, not just a warn.
2. **Bring `space_dek` under tenant scope.** Change its signature to take the tenant transaction `&mut PgConnection` (or call `with_tenant` with the resolved `SpaceId`) and use that connection for the read/mint, so RLS and atomicity hold. *Risk:* signature churn in `destinations.rs` (two call sites) and a duplicated mint path with `put`. *Mitigation:* extract one shared `dek_for_space(conn, secrets, space_id)` used by both `put` and `space_dek`; keep it crate-internal; add integration tests that a destination in space A cannot read/write a DEK from space B, with `REQ-065` / `REQ-046` in the names.
3. **Distinguish decryption failures from outages.** Add `AppError::SecretIntegrity` (non-retryable, generic client message) raised only at AEAD/UTF-8/wrap-length failures crossing from `secret_box.rs` into the store; keep DB errors as `Unavailable`. Emit `tracing::error!` + a counter tagged with `space_id`/`bot_id` (never the value) on every failed open. *Risk:* a new public error variant touches the API error mapping and `is_retryable` / `is_client_fault`; a false positive would suppress retries for a genuinely transient fault. *Mitigation:* map only deterministic crypto failures to it; test that a tampered ciphertext yields `SecretIntegrity` while a dropped DB connection yields `Unavailable`; keep the wire status inside the stable envelope (DEVIATION entry in `docs/PARITY.md` if the status changes).
4. **Safe, restartable rotation.** Make `rekey_space_keys` try `new` first and skip rows that already unwrap under it, batch the `FOR UPDATE` into chunks to shorten lock hold, log progress and the offending `space_id` on failure, and add a `--verify` dry-run that unwraps every DEK under `new` without writing. Document the overlap rule: keep the app on the old key until rekey completes, then roll it forward. *Risk:* "try new first" relies on AEAD failure as the only discriminator, so a corrupt row could be misclassified. *Mitigation:* treat both-unwrap-fails as a hard error; commit per batch inside its transaction with an explicit rotation state (additive migration), and keep `rotated_at` authoritative for skip decisions.
5. **Boundary validation and lifecycle hygiene.** Add CHECK constraints for 12-byte nonces and ciphertexts larger than the 16-byte GCM tag on both tables; stop resetting `created_at` on `put` upsert (preserve it, add `updated_at`); record aggregated reveal count/latency metrics (no values) so anomalous reads are visible. *Risk:* a CHECK migration must first clean or quarantine malformed rows, and a fixed length could reject a future algorithm change. *Mitigation:* ship constraints in a versioned migration with a preflight audit query; store an algorithm-version column if a second AEAD is ever planned; keep reveal metrics aggregated only (no secret material, REQ-054).

## Cross-cutting risks / sequencing

- Order 2 → 3 → 1 → 4 → 5: close the tenant/atomicity gap first (correctness), then error classification/observability, then the startup guard, then rotation safety, then DB constraints. Do 2 before changing destinations behavior.
- Do not duplicate worker #393 (architecture) on this module, or the `secret_box.rs` worker on primitives: this proposal covers store-level reliability only.
- No externally visible wire/data-format change unless recorded in `docs/PARITY.md` and approved (AGENTS.md); the new error variant and any rotation CLI flag need that entry.
- Verification gate per step: `cargo fmt --check`, `clippy -D warnings`, and infra integration tests against real Postgres — cross-tenant DEK isolation, wrong-key reveal, tampered-ciphertext classification, rekey-then-reveal, rekey idempotency — with `REQ-046` / `REQ-065` in test names (`tools/trace_check.py` counts declarations only).

## Out of scope

KMS/HSM integration (DEC-10 option (b)), backup/escrow of the master key (ADR-020 declines it), the crypto primitives in `secret_box.rs`, the shell-out executor's handling of `BOMA_SECRET_*`, and the destinations store's validation rules beyond DEK acquisition. This proposal is limited to reliability of this store and its rotation path.
