# 0029 — apps/web/app/integrations/setup/page.tsx — architecture lens

- Target: `before-m5` (v0.3.0-rc5), module `apps/web/app/integrations/setup/page.tsx` (16 lines).
- Read-only review; no code edited. Substance lives in `apps/web/components/integrations/integrations-setup.tsx` (211 lines, `"use client"`), read this session, plus `lib/api/rpc.ts` (M10 integrations types), `tests/integrations.spec.ts`, `lib/i18n.ts`, `spec/08-ui-ux.md` §8.7, REQ-032/034/048.
- Spec anchors: §8.7 (`/integrations/setup` — post-OAuth landing: confirm the connection, choose which bots may use it, surface the partial-install report rather than a green check), REQ-034 (skipped parts named with reasons), REQ-048 (messaging installs bind one bot).

## The page's role, today

The page is the right shape: a thin server component wrapping a client island in `<Suspense>` (the island reads `useSearchParams`, so the boundary is required). Every other concern — data loading, the phase machine, the three sections, chrome, copy — was pushed into one client component. `fallback={null}` means a blank white frame while the shell resolves; the real skeleton exists one level down but is unreachable until hydration. The architecture is accidental, not designed: routing/metadata belong here, rendering belongs in `components/`, and v0.4.0 should make that boundary deliberate.

Confirmed observations (read this session):

- **Silent failure conflation.** `Promise.allSettled` swallows rejections from all three RPCs. If `messaging/list` 404s (the existing Playwright test mocks exactly that) or the network drops, the screen renders "ready" with empty sections — indistinguishable from "nothing installed yet". There is no `error` phase, no retry, no correlation id, violating the §8.9 error-copy rule (one sentence what happened, one what to do, id behind "details").
- **Phase machine is half a state machine.** `Phase = loading | ready | partial`; `partial` is set only when a plugin reports skipped parts, then coerced back to `ready` by the final `setPhase` unless it was already `partial`. Connector install failures, messaging install failures, and a missing `installed` confirmation are all invisible in the state model. "partial" is also doing double duty as a data property of one section, not a screen-level phase.
- **Spec gap, recorded but open.** §8.7 promises "choose which bots may use it"; the component deliberately says space-wide tools and documents the deferral in a comment only ("there is no per-bot gate that does not exist"). A GUESS recorded in a comment is not recorded — it belongs in `docs/STATE.md` with the spec-vs-code decision for v0.4.0. Messaging installs *are* per-bot (installed-time `botId`), so the screen already has the data to offer at least a per-installation bot view/switch if the product wants it.
- **Confirmation is unvalidated echo.** `?installed=slack,github` renders the raw comma-separated param back as "Installed: …" without checking it against the server state. React escapes it (no XSS), but a stale/forged param shows a confirmation for something the space may not hold, undermining the "nothing here is a false negative/positive" promise in the file's own docblock.
- **Chrome duplication risk.** `max-w-2xl` container + back-to-app link + title pattern is hand-rolled here and in other post-install/onboarding landings (sign-in/sign-up/invite/reset-password all share the `Suspense fallback={null}` shell). No shared post-install layout, no `metadata` export (tab title is generic), no `loading.tsx`/`error.tsx` at the route.
- **No empty state.** First-time users (OAuth returns before any install completes, or all three lists are empty) see a bare header. §8.7 is a *landing*; it should orient (what was attempted, what to do next, link to `/app/` and the catalogue), not render nothing.
- **Type honesty.** `skipped: Array<Record<string, unknown>>` and `String(part["part"] ?? part)` — the wire shape is un-narrowed at the boundary; the screen renders whatever the server sent, including non-string scalars.

## How it should evolve in v0.4.0

Keep the page a server component; make the boundary real: metadata + route-level loading/error here, a decomposed client island underneath, typed failure modes from `lib/api/rpc.ts`, the §8.7 screen composed from BoardUI section/card/alert components with semantic tokens only (`bg-background-primary-default`, `border-border-button-default`, `rounded-2xl`/`3xl`, composite type utilities — already the case; keep it).

## Proposals

### 1. Give the route real App-Router semantics: metadata, `loading.tsx`, `error.tsx`, non-null Suspense fallback
Add `export const metadata` ("Integrations — Boma Bot", `robots: noindex` — this is an authenticated internal landing), a `loading.tsx` mirroring the existing skeleton (single source: extract `IntegrationsSetupSkeleton`), a client `error.tsx` with the §8.9 two-sentence copy and a `reset()` retry, and pass a real JSX fallback to the page's `<Suspense>` instead of `null`. Risks: (a) `error.tsx` must be a client component and adds a second failure surface that must not leak internals — keep it to the safe envelope; (b) skeleton drift between `loading.tsx` and the island's internal skeleton — mitigate by sharing one component; (c) negligible axe/golden impact, but re-run the REQ-034/048 Playwright specs and a11y suite.

### 2. Replace `allSettled`-and-swallow with a typed per-section resource hook and an honest failure model
Introduce `useIntegrationsData()` (or extend `lib/api/rpc.ts` with `useConnectionSection`-style helpers) returning `{ connections, marketplace, messaging }` each as `{ status: idle|loading|ready|error, data?, error?, retry }` built on `RpcError`'s machine codes, `AbortController` on unmount, and a reload token. Render per-section inline alerts (`text-text-error-primary`, two-sentence copy, correlation id behind "details") instead of a silent empty screen; only the confirmation banner stays `aria-live="polite"`. Delete the `Phase` union entirely — "partial install" becomes a derived property of the plugins section (`installedPlugins.some(p => p.skipped.length > 0)`), not a screen phase. Risks: (a) shared hook couples three sections — a change for one can regress another's retry; keep sections independent; (b) tightening `RpcError instanceof` checks must still route network-down (non-RPC throwable) to the generic error path — add that test case; (c) touching the loading path can regress `aria-busy` expectations in `tests/a11y.spec.ts`; run it before merge. Highest value-to-risk ratio of the five.

### 3. Compose the screen from BoardUI primitives and close the §8.7 confirmation gap deliberately
Extract `MessagingSection`, `PluginsSection`, `ConnectorsSection`, `InstallConfirmation` (props in, no fetching), render skipped parts with a BoardUI `alert`/`badge` trio (text + icon, never colour-only) inside the plugin card, keep the source link with `rel="noopener noreferrer nofollow"`, and validate `?installed=` against server state: only celebrate platforms present in `messaging.list`/`marketplace.list` (case-insensitive match), otherwise show a neutral "we couldn't confirm that install — check the catalogue" line. Record in `docs/STATE.md` the §8.7 decision: either (a) ship the "choose which bots may use it" assignment flow (messaging-only per-bot binding UI exists as data), (b) amend spec §8.7 to the space-wide reality with an ADR, or (c) keep the deferral but move it out of a comment and into the tracker. Do not do (a) silently. Risks: (a) widest diff — axe and golden churn, land behind the integrations Playwright gate in slices; (b) validating the query param against async server state creates a flicker state (confirm → downgrade) — resolve by rendering the confirmation only when matched, with one render of nothing beforehand; (c) any new catalogue keys need fr/he translations or documented English fallback per `docs/UI.md`.

### 4. Narrow the wire types at the boundary and add the missing empty state
Replace `skipped: Array<Record<string, unknown>>` narrowing with a typed guard (`parseSkippedPart` → `{ part: string; reason?: string } | null`) and drop unrenderable entries with a count ("2 unnamed skipped parts") instead of `String(part)` on arbitrary objects. Add a first-run empty state: one sentence ("Nothing installed yet"), one primary action to the catalogue (`/integrations` or the plugin source flow), one secondary link back to `/app/`. Risks: (a) hiding skipped parts entirely would breach REQ-034 — the "unnamed parts" fallback is mandatory, never drop silently; (b) an empty-state CTA to a catalogue route that does not exist yet is dead UI — gate it on the route's presence or point at `/app/`; (c) wire-shape parsing must match `crates/api/src/wire.rs` exactly — verify against the Rust side, do not guess.

### 5. Metadata-driven OAuth landing semantics and telemetry
Since the OAuth callbacks land here, make the page the observability seam: a single structured client event ("integrations.setup.viewed", `{ justInstalled, confirmed, partialCount }` — no PII, no tokens) so install success/partial rates are measurable, and strip the `installed` param from the URL after validation (`router.replace("/integrations/setup", { scroll: false })`) so a refresh doesn't re-announce and the confirmation doesn't linger in history. Risks: (a) analytics must honour the no-secrets rule — the param carries platform names only, but verify no token ever rides it (GUESS: confirm with the OAuth callback author); (b) `router.replace` inside an effect can fight the Suspense boundary — run after validation, guarded by `useRef`; (c) new telemetry needs the privacy note in docs and opt-out consistency with the rest of the app.

## Explicit non-goals
No client-side authorization theater, no new integration surfaces beyond the spec, no BoardUI Pro components, no per-bot gating logic that the backend does not enforce, no restyling off the semantic tokens. The server remains the only boundary; this screen only reports it honestly.
