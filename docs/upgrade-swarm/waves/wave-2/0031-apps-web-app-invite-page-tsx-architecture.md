# 0031 — apps/web/app/invite/page.tsx — architecture lens

- Target: `before-m5` (v0.3.0-rc5), module `apps/web/app/invite/page.tsx` (15 lines).
- Read-only review; no code edited. Sister file `apps/web/components/invite/accept-screen.tsx` (133 lines) read — the page is a pure delegate; the substance, and the debt, lives there. `AuthShell`, `lib/api/rpc.ts`, sign-in screen, `spec/08-ui-ux.md §8.2`, REQ-042, `docs/UI.md`, `docs/TRACEABILITY.md` also read.
- v0.4.0 scope: the invite-accept screen structure and its token surface. Keep BoardUI semantic tokens (`bg-background-*`, `text-text-*`, `text-title-*/text-headline-*/text-body-*` composite utilities) and `cx()`; no new literal colors, no second design system.

## The page's role, today

`/invite?token=<token>` is a public, anonymous entry route. The page is exactly what it should be — a server-component shell wrapping `<InviteScreen />` in `<Suspense>` (required because `useSearchParams` forces a client-side read under the static export, ADR-013; spec §8.2 chose query param over route param for the same reason). That shape should survive v0.4.0: routing and any server-side gate live in `app/`, rendering in `components/`. The weaknesses, confirmed this session:

- `fallback={null}` renders a blank page until the client bundle hydrates and the preview resolves — a flash of nothing on the one route an external invitee's first touch, and a CLS/LCP cost the loading skeleton inside `InviteScreen` already solves internally but the route does not reuse.
- No `export const metadata` — tab title/description are generic, and nothing marks the route `noindex` (an invite URL in an index leaks nothing by itself, but it should never be a landing result).
- `accept-screen.tsx` conflates failure modes: `invitationPreview()` throws `RpcError("NOT_FOUND")` for *any* non-OK status and the `.catch()` maps network-down and HTTP 500 identically to "unavailable" — no retry path, unlike the sign-in screen's error phase with `Button` + `common.retry`.
- The `accept()` catch sniffs `error.code === "NOT_FOUND"` structurally (`typeof error === "object" … in error …`) instead of the typed `RpcError` (`lib/api/rpc.ts`); the rest funnels to `invite.error.generic`.
- `preview.expiresAt` renders raw (presumably ISO) and `preview.role` renders the raw enum — neither goes through `Intl` nor the catalogue, against the `docs/UI.md` Intl/catalogue rules.
- **Spec gap:** §8.2 states expired or revoked tokens must show a *specific* message and "a way to request a new invitation." The current screen shows one generic `invite.unavailable` sentence and a bare `/sign-in` link — no expiry-specific copy, no request-a-new-invite affordance. CONFIRMED by reading both files; not yet in `docs/STATE.md` as a DEVIATION.
- `invitationsAccept` carries no idempotency key (`call()` sends no idempotency header); the double-submit window is closed only by the client-side `disabled={busy}`. Server-side accept-once semantics are covered by tests (`req_042_accepting_twice_consumes_the_invitation_once`), so this is defense-in-depth, not a live bug.

## Token surface (where the credential lives)

CONFIRMED: token travels as `?token=` query param (spec §8.2, signed off in STATE.md DEV-02); preview fetch uses `credentials: "omit"` with `encodeURIComponent(token)`; accept sends the token in the RPC POST *body*, never in a URL; both client-side navigation paths (`/sign-in`, `/sign-up`) carry it percent-encoded inside `next=`, and the sign-in screen already restricts `next` to same-origin paths (`startsWith("/") && !startsWith("//")`) — the round trip does not open an open-redirect.
Residual exposure: (a) the token persists in browser history until `router.replace("/app/")` after accept (and on the abandoned path, forever); (b) it transits `/sign-in?next=…`, also in history; (c) no `referrer` policy on the route — the screen renders no outbound links, but the default document referrer still leaks the full URL to any origin the browser later navigates to; (d) proxy/correlation logs — already mitigated server-side (STATE.md: logs record `/api/v1/invites/{token}`). None of this is fixable by hiding the param; it is inherent to the static-export decision and must be documented, not re-architected.

## Proposals for v0.4.0

### 1. Make the route shell honest: metadata + `noindex` + real `loading.tsx` + `error.tsx`
Add `export const metadata` (`title: "You were invited — Boma Bot"`, `robots: { index: false }`, `referrer: "no-referrer"`), a route `loading.tsx` that renders the same scaffold as the component's loading phase (reusing the `aria-hidden` skeleton), and an `error.tsx` client boundary with retry. Keep `page.tsx` a server component with `<Suspense>` as today. Risks: (a) duplication between `loading.tsx` and the in-component skeleton — extract one shared `InviteSkeleton` to avoid drift; (b) `noindex` is technically a behavior change for a public URL, though it can only help; flag in `docs/PARITY.md` if any parity gate disagrees; (c) golden/axe churn on the REQ-042 path — run the REQ-042 Playwright spec and axe before merge.

### 2. Type the failure taxonomy; split "unavailable" from "unreachable"
Introduce `isRpcErrorCode(error, code)` in `lib/api/rpc.ts` (or a small `lib/invite/` module): `instanceof RpcError` first, structural sniff dropped. In `InviteScreen`, map `NOT_FOUND` → the not-available sentence, but map network/5xx to a distinct, retryable phase (mirror the sign-in error phase: icon + `invite.error.unreachable` + `common.retry` with a `reloadToken`). `invitationPreview()` already throws `RpcError` with status — no wire change. Risks: (a) any non-`RpcError` throwable (TypeError from `fetch`) must funnel to the retryable branch, which is the safe direction, but needs an explicit network-down test; (b) catalogue additions (`invite.error.unreachable`) need fr/he strings or documented English fallback per `docs/UI.md`; (c) Playwright REQ-042 needs a network-failure case added; wording review by whoever owns the catalogue.

### 3. Close the §8.2 "request a new invitation" gap deliberately
Add an `invite.request-new` affordance on the unavailable state: a plain-language line telling the visitor to ask the sender (or the space operator) to re-send, plus — only if the RPC contract exposes one — a request endpoint; today it does not (GUESS: verify against `spec/openapi.yaml` and `spec/03-api-contract.md` before wiring a button; do not invent an endpoint). Record the wording interim decision in `docs/STATE.md`, not just in JSX. This is a spec-compliance fix, not a feature. Risks: (a) without a contract, the affordance is copy-only — easy to misread as a promise the deployment cannot keep; keep it to "ask the person who sent you this link"; (b) if a request-invite endpoint is added later, this becomes a mutation needing its own idempotency and rate-limit review; (c) catalogue and golden updates again — bundle with proposal 2, not separately.

### 4. Decompose `InviteScreen` into hook + presentational states; format what is rendered
Split into `useInvitationPreview(token)` (AbortController, `reloadToken`, exhaustive `"loading" | "ready" | "unavailable"` machine) and `InviteLoading` / `InviteReady` / `InviteUnavailable` components (props in, callbacks out, no fetching in children). In the ready state, render `expiresAt` through `Intl.DateTimeFormat` bound to the active locale, and map `role` through the catalogue (`invite.role.admin|member|…` with raw-value fallback). Keep `invite/page.tsx` untouched except removal of the component-level skeleton duplication. Risks: (a) widest diff of the four — best landed as a pure refactor commit before behavior changes from 2–3; (b) `Intl` output depends on ICU availability in the static-export runtime — Node/full-ICU is fine, but assert one fr date rendering in a unit test; (c) role catalogue keys must match the server's role vocabulary exactly — verify against `spec/02-data-model.md` first (GUESS this session).

### 5. Accept-flow hardening (small, optional)
Send an `Idempotency-Key` header from `invitationsAccept` if/when `lib/api/rpc.ts` gains header support (the backend already guarantees accept-once), otherwise document the gap in `docs/STATE.md`; and after accept, prefer `router.replace("/app/")` (current) — keep it, since it erases the token URL — but note the same cannot be done on the abandoned path; mitigate by proposal 1's `no-referrer` and by not rendering outbound links on the ready screen. Risks: (a) adding a header now without a backend consumer is dead weight — defer until the RPC client grows an idempotency helper; (b) no user-visible change; risk is scope creep, keep it out of the UI commit.

## Explicit non-goals
No client-side authorization decisions (the server is the only boundary — keep it), no token in a route param (spec forbids; static export), no removal of the `next=` round trip, no new BoardUI Pro dependency, no "remember my invite" persistence. The page stays a thin server delegate; the token surface stays query-param by design; v0.4.0 should spend its budget on honest failure states, the §8.2 gap and route chrome — not on re-plumbing what the spec already fixed.
