# v0.4.0 reliability proposal — `migrations/0041_routines_email_senders.sql` (worker #494, lens: reliability)

- **Status:** PROPOSAL (read-only review; no source or migration changed). CONFIRMED = verified by reading files in this worktree; GUESS = needs a real-Postgres/test/oracle run.
- **Scope:** `routines.email_senders text[] NOT NULL DEFAULT '{}'` (0041:6-7) and its read path in `crates/app/src/usecases.rs::mail_inbound` (:2190, :2203-2213), writes via `routines_create`/`routines_update` (:4931-4991; rpc.rs:1229-1231, :1268), and the sibling allowlist in `0040_bot_mail.sql::bot_mail_rules.allowed_senders jsonb`. Every hardening below is **additive**: a NEW migration / NEW object only; 0041 itself and all existing columns, constraints, policies and rows stay untouched.
- **Trace:** REQ-047 (`spec/01-requirements.md:383-389`); REQ-023/024; `docs/STATE.md:844-857` (bot allowlist is capped at 20 and normalized; no such rule is stated for a routine's senders); `docs/upgrade-swarm/waves/wave-20/0442-...-reliability.md` (shared `routines` RLS findings).

## Summary

The column is a one-line `ALTER TABLE` with **no shape constraint and no write-time validation**, while the value it is compared against is normalized (lowercased) on the inbound path. Reliability therefore rests on the caller storing a lowercase, well-formed, NULL-free, bounded array; nothing in the database or the routine write path enforces that. The result is mostly *silent* failure: a mis-cased or malformed entry simply never matches and mail is held/dropped instead of waking the routine, and a single NULL element can turn every inbound mail for that bot into a hard error. RLS is not new here — the column inherits the permissive `routines` policy — but the mail lookup deliberately runs under a system context, so a misconfigured tenant/system setting changes routing silently rather than loudly.

## Failure modes

### Array integrity (A)

- **A1 (HIGH, CONFIRMED mechanism / GUESS impact):** `NOT NULL` constrains the column, **not its elements** — `text[]` freely holds NULL members, empty strings, whitespace and duplicates. The reader decodes into `Vec<String>` (`rows.rs:568`, `routines.rs:42-67`). GUESS: a NULL element makes sqlx's array decode fail, so `routines.list` (:2203) errors and the whole relay POST returns an error — no hold, no drop, no run. Verify with a real-Postgres test before sizing.
- **A2 (HIGH, CONFIRMED):** case/format mismatch is silent. The inbound sender is lowercased (`:2190`, `mail.from.to_ascii_lowercase()`) and compared with `admitted == &sender` (`:2211`), but `email_senders` is passed verbatim from RPC (`:1268` → `:4942` → `:4984`) with **no `Email::new` parse and no lowercase normalization** — unlike `mail_policy_set` (`:2422-2427`). A stored `Tracker@Parcels.Example` (or one with trailing space) never matches its own lowercase mail: the routine silently never wakes.
- **A3 (MED, CONFIRMED):** no cap and no dedup. The bot allowlist is capped at 20 and validated (`usecases.rs:2417-2427`), but `email_senders` can be an arbitrarily large array; every inbound mail loads all routines of the bot and linearly scans every entry (`:2203-2213`). A bulk import or hostile RPC inflates scan cost and row size with no DB-side backstop.
- **A4 (MED, CONFIRMED):** two allowlist representations with different rules. If a sender is on both the bot's `allowed_senders jsonb` (validated, ≤20) and a routine's `email_senders` (unvalidated), the member/allowlist branch wins (`:2248`) and a conversational run starts — the routine silently does **not** fire. Operators reading only one list cannot predict routing.

### Constraints (C)

- **C1 (HIGH, CONFIRMED):** 0041 adds no CHECK at all, in a schema where `bot_mail_rules.policy` has `CHECK (policy IN ('hold','drop'))` (`0040:11`). Direct SQL, imports and any future writer can store any array shape.
- **C2 (MED, CONFIRMED):** no cross-object invariant: nothing requires a routine's sender entries to be lowercase/canonical, nor ties them to the space the routine belongs to. A row with a sender from another space is storable and, under a system context, actionable.
- **C3 (LOW, CONFIRMED):** as with worker #442's C5, `updated_at` is app-written only; `email_senders` changes by direct SQL leave no DB-enforced timestamp.

### RLS / tenant isolation (R)

- **R1 (HIGH, CONFIRMED):** `routines` has one PERMISSIVE ALL policy `space_id = current_space_id() OR boma.is_system()` under FORCE RLS (`0014:46-60`); 0041 adds no policy. The mail flow reads routines under `TenantContext::System { WebhookDelivery }` (`:2168`, `:2203`), so `is_system()` is true and `space_id` is not consulted — the lookup is keyed only by the globally unique `bot_id`. Since `is_system()` accepts **any** non-empty `boma.system_reason` (`0002_m1.sql:38-42`), a misconfigured setting silently broadens which routines mail can wake, rather than failing closed.
- **R2 (MED, CONFIRMED):** a forgotten `boma.space_id` yields an empty result by design (`0002_m1.sql:7-9`). On a member-context routine read that means "no routines", so a legitimate sender is held/dropped instead of admitted — a silent misroute, not an error.
- **R3 (MED, CONFIRMED):** no audit of `email_senders` changes. Drift (who added a sender, under which context) is invisible, complicating incident review of an admission that started a run.

## Concrete hardening (additive only, prioritized)

1. **H1 — P0, array integrity (closes C1/A1/A3).** New `0065_email_senders_integrity.sql`: add `CHECK (array_position(email_senders, NULL) IS NULL)`, `CHECK (NOT '' = ANY(email_senders))` and `CHECK (cardinality(email_senders) <= 20)`, each `NOT VALID`, then `VALIDATE CONSTRAINT` only after a staging read confirms no violating rows. This is pure defense-in-depth; the app validator stays primary. *Risks:* validation blocks a release if bad rows exist (safe failure) and rejecting previously storable arrays is externally visible — record in `docs/PARITY.md` with an ADR. The cap mirrors the bot allowlist but is a new rule for routines (GUESS: acceptable, confirm no golden seeds >20).
2. **H2 — P0, normalize on write (closes A2/A4).** In `routines_create` and `routines_update`, parse each entry with `boma_domain::Email::new` and `to_ascii_lowercase()`, cap at 20, dedup — the same helper path `mail_policy_set` already uses (`usecases.rs:2422-2427`). No wire/field change. *Risks:* mixed-case input previously accepted now normalizes (or is rejected); a `RoutineView` round-trip may change casing — verify goldens/contract tests first and note any externally visible change in `docs/PARITY.md`.
3. **H3 — P1, trigger + audit (closes A1/A3/A4/C3/R3 for direct writes).** Add `BEFORE INSERT OR UPDATE` trigger `boma.validate_email_senders()` rejecting NULL/blank/untrimmed/malformed entries, and an append-only `routine_email_sender_changes(routine_id, space_id, changed_at, is_system)` table populated by a trigger. **Gate both triggers with `WHEN (NEW.email_senders IS DISTINCT FROM OLD.email_senders)`** — the hot dispatch `record_fired` UPDATE (routines.rs:211-217) must not pay for them. Keep raw addresses out of the audit rows (PII rule). *Risks:* an IMMUTABLE SQL helper called from a CHECK that uses `unnest`/subquery must be verified against real Postgres; a trigger is the safer home for format rules. Trigger overhead on bulk routine imports; benchmark.
4. **H4 — P1, fail-closed RLS for new paths (partial R1).** Add `boma.system_reason_valid()` and use it in any NEW policy on routine-adjacent tables; add a CI/read-only guard asserting the mail flow passes a verified `bot_id`. *Risks:* tightening existing `is_system()` is non-additive and needs its own ADR (worker #442 R2); do not silently change current behavior.
5. **H5 — P2, tests (REQ-id named, testcontainers, RLS on).** `req_047_a_mixed_case_routine_sender_wakes_its_routine`; `..._a_null_sender_element_is_rejected`; `..._an_oversize_sender_array_is_rejected`; `..._a_sender_on_both_lists_starts_the_conversational_run`; `..._a_missing_tenant_setting_never_admits_by_accident`; plus a concurrent-write assertion on H1/H3. All claims above are CONFIRMED from source except items explicitly marked GUESS.
