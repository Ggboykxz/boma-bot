# v0.4.0 reliability proposal — `migrations/0050_invitation_inviter.sql` (worker #512, lens: reliability)

- **Status:** PROPOSAL (read-only review; no source or migration changed). CONFIRMED = verified by direct reads in this worktree; GUESS = needs a live-DB test or oracle run.
- **Scope:** the one `ALTER TABLE ... ADD COLUMN inviter_user_id text REFERENCES users(id) ON DELETE SET NULL`, read together with `0002_m1.sql` (`invitations` RLS, `users` global), the writer (`crates/infra/src/stores/invitations.rs:66-77`), the readers (`invitations.rs:96-102`, `crates/infra/src/stores/users.rs:104-113`, `crates/app/src/usecases.rs:8842-8856`) and the deletion path (`crates/infra/src/stores/accounts.rs:198-230`). Spec anchors: REQ-042 / REQ-043 / REQ-045.
- **Constraint:** additive only. Everything below is a *new* numbered migration, a `COMMENT`, or a test; nothing rewrites 0050. No `DROP COLUMN`, no type change, no destructive `UPDATE`, no back-fill.

## Current shape (CONFIRMED)

`invitations` is tenant-scoped (`space_id NOT NULL`, RLS ENABLE+FORCE, policy on `space_id` OR `boma.is_system()`, from `0002_m1.sql:226-236,267-277`). `users` is global, has no RLS, and is the FK target. The new column is nullable, has no default, no index and no CHECK. Existing rows become NULL (metadata-only add, no rewrite). The member path writes `context.user_id()` (`usecases.rs:305-316`); the anonymous preview reads the id on a system path (`tenant::as_system(SystemReason::Authentication)`) and resolves the name with `users.find()` — which selects the **whole row including `password_hash`** — then keeps only `.name` (`usecases.rs:8854`).

## Failure modes

### Foreign key

- **F1 (HIGH, CONFIRMED structural; GUESS exploitability):** the FK points at global `users(id)` and referential checks bypass RLS/tenant GUCs, so `inviter_user_id` can name *any* user, including one with no `space_members` row in the invitation's space. Today the writer is self-consistent (self id only), but a system/future writer can store a foreign inviter and the preview will display that stranger's name. "Who invited you?" is spoofable; no DB-level membership invariant exists.
- **F2 (MED, CONFIRMED structural; GUESS impact):** no index on `invitations.inviter_user_id`. `ON DELETE SET NULL` must find every referencing row, so user deletion (`accounts.rs:226`) sequentially scans `invitations`. Harmless when small, degrades as invitations accumulate.
- **F3 (MED, CONFIRMED code, GUESS operational impact):** inline `ADD COLUMN ... REFERENCES` cannot be declared `NOT VALID`; it takes `ACCESS EXCLUSIVE` on `invitations` and a share lock on `users`. Existing NULLs make validation cheap, but a live `users` table can still stall the migration; the file is not idempotent (a re-run after partial failure errors).
- **F4 (MED, CONFIRMED):** `ON DELETE SET NULL` silently erases attribution. In contrast SCIM deprovision only sets `users.deactivated_at` (`accounts.rs:185`), so the FK never fires and the preview still renders a deactivated person's name (no `deactivated_at` check at `usecases.rs:8848-8855`). Two "user left" paths give different visible results.
- **F5 (MED, GUESS):** the referential `UPDATE` generated by `SET NULL` runs on `invitations`, which has RLS FORCE. If a delete happens without a system GUC (operator SQL, a future non-system path), the action may be denied and the user delete fails. `delete_account` uses `as_system` today, so the shipped path is fine — verify the precise RLS/referential-action interaction by test.

### RLS / tenancy

- **T1 (LOW, CONFIRMED):** the new column adds no policy surface; RLS still keys only on `space_id`. The real isolation risk remains GUC spoofing (`boma.space_id`/`boma.system_reason`, see wave-21 0474/T1) — not introduced by 0050. Preview's system read is intentional and must stay a narrow projection.
- **T2 (MED, CONFIRMED):** the anonymous, token-gated preview loads a global user row containing `password_hash` into app memory. It is discarded, but a future DTO/logging change turns a token-only caller into a secret-disclosure path.
- **T3 (MED, CONFIRMED):** `find_by_token_hash` filters neither `status` nor `expiry`, so a consumed/expired invite still yields an `inviter_user_id`; validity depends entirely on the use-case check at `usecases.rs:8839` (cross-ref wave-15 0350, H1/H2).

### Audit

- **A1 (MED, CONFIRMED):** preview is an unlogged, token-gated PII disclosure (space name + inviter name). `0052_invite_accept_audit.sql` records only `security.invite_accepted`; there is no preview/failed-token kind, so guessing or scraping tokens is invisible. Rate limiting is a separate generic mechanism (not in `0023_rate_limits.sql`) — GUESS whether preview is covered.
- **A2 (MED, CONFIRMED):** `ON DELETE SET NULL` emits no audit event. `account.deleted` does not say which invitations lost their inviter, so the "record who issued" intent decays silently on hard deletion.
- **A3 (LOW, GUESS):** a DB trigger auditing the FK action would run inside a referential action where the tenant GUC may be absent and `audit_events` is itself RLS-protected; it could fail or attribute the wrong space. Prefer app-level audit in `delete_account`.

## Concrete hardening (prioritized, all additive)

1. **P0 — index the FK (F2):** new migration `CREATE INDEX invitations_inviter_user_id_idx ON invitations (inviter_user_id)`. *Risk:* one extra index write per invite; plain `CREATE INDEX` takes `ACCESS EXCLUSIVE` (sqlx migrations are transactional, so `CONCURRENTLY` is unavailable) — schedule a low-traffic window.
2. **P0 — membership invariant (F1):** new migration adds a `BEFORE INSERT OR UPDATE ON invitations` trigger that, when `NEW.inviter_user_id IS NOT NULL`, requires `EXISTS (SELECT 1 FROM space_members WHERE space_id = NEW.space_id AND user_id = NEW.inviter_user_id)`. A plain FK cannot express a tenant-scoped pair; a trigger can. *Risk:* rejects system/admin/SCIM-created invites whose inviter is not a direct space member — audit those call sites first; if unacceptable, fall back to app-level validation plus tests (no DB enforcement).
3. **P1 — prove the delete paths (F5/F4):** real-Postgres tests: `DELETE FROM users` under `as_system` succeeds and NULLs only the expected rows; the same delete without system GUC is probed and the outcome recorded; deactivated-inviter preview behaviour is pinned by a test before any change. *Risk:* test-only; if F5 is confirmed, the fix belongs in the deletion caller (always `as_system`), not in 0050.
4. **P1 — narrow the preview projection (T2):** add `users.name_of(id)` selecting only `name` and switch `invite_preview` to it; keep `MemoryUserStore` in sync. *Risk:* port/test churn; internal only, no externally visible DEVIATION, but must not change the "unknown invite → NotFound" response.
5. **P1 — audit unlink (A2/A3):** in `delete_account`, append one event per affected invitation before the delete, carrying space id and invitation id, **never** token/email/name. This needs a new kind (e.g. `security.inviter_unlinked`) via the established 0049/0052 pattern of dropping and re-adding `audit_events_kind_check` in a *new* migration. *Risk:* that constraint rewrite is not strictly additive under a literal reading — defer to an ADR/operator sign-off; bulk deletes can be noisy; NULL `space_id` rows need 0045-compatible handling.
6. **P2 — close the replay surface (T3/A1):** adopt wave-15 0350 H1/H2 so a consumed/expired token cannot reach the preview, and add failed/preview token telemetry only if the operator accepts the log volume. *Risk:* touches app ports and audit-kind policy; out of scope for the migration itself.

## Additive-only guarantee

Items 1-3 and 6 are new index/trigger/test/metadata files; item 4 is an app-store change; item 5 is the only one that rewrites an existing CHECK and is explicitly gated behind an ADR. No change to 0050's checksum, no data mutation, no back-fill; applied-migration hash chain stays intact.
