# 0141 — crates/api/src/openapi.rs — architecture lens

Target: `before-m5` (v0.3.0-rc5, v0.4.0 proposal), module `crates/api/src/openapi.rs` (82 lines). Read-only review; nothing edited. Files read: `openapi.rs`, `lib.rs`, `router.rs`, `health.rs`, `screen.rs`, `crates/conformance/tests/contract.rs`, `spec/openapi.yaml`, `docs/adr/003-interface.md`, `crates/api/Cargo.toml`, and sibling wave-8 proposal 0105. Claim status: CONFIRMED = read in this tree; GUESS = inferred, needs verify.

## Structure today (CONFIRMED unless marked)

- One `ApiDoc` unit struct with `#[derive(OpenApi)]` + `#[openapi(...)]`: 5 paths, 8 schemas, 3 tag entries; `document()` builds a fresh `OpenApiDocument` on every call. The header is sound: the doc is generated from annotated handlers, never hand-written; the RPC procedure surface stays in `spec/03-api-contract.md`.
- The only consumer of `boma_api::openapi::document()` is `crates/conformance/tests/contract.rs:19`. No HTTP route serves the document: a repo-wide grep for `openapi.json|swagger|document()|ApiDoc` found no handler in `router.rs`, `pages.rs`, `public.rs` or `automation.rs`. ADR-003 §44-45 says the HTTP surface is "served as a generated `openapi.json`". Today it is a test fixture only. GUESS: oversight, not a recorded deviation.
- The contract test compares generated paths only: presence in the spec, exact `operationId`, status codes as a subset. It does NOT compare `info`, `tags`, `components`, nor the reverse direction (a spec path with no annotation). Both metadata drift and missing annotations are silent.
- `info.title` is "Boma Bot HTTP interface"; `spec/openapi.yaml:3` says "Bots platform HTTP interface" and carries a `summary` the generated doc does not model. Lines 44-45 declare two identical `name = "ops"` tags; the second description is "The sealed screen stream", yet `screen.rs:62` also tags `screen_target` as `ops`. Spec tags are ops/auth/public/webhooks/devices/admin. The spec title may be original-brand residue — owner decides, do not edit spec here.
- Coverage: 5 annotated paths vs 28 `.route(...)` declarations in `router.rs` and 20 paths in `spec/openapi.yaml`. Absent from the doc: auth flows, SCIM, public links, webhooks, device pair/session, monitoring. Some are unimplemented milestone gaps (the header anticipates these); others are implemented and unannotated — the current test cannot tell the two apart.
- `info.version = "1.0.0"` matches the spec; read it as the HTTP contract version, not the product's 0.4.0 (GUESS — confirm before anyone "fixes" it to 0.4.0).

## Proposals for v0.4.0

1. **Serve the document, closing the ADR-003 gap.** Add a `Json<document()>` handler in `openapi.rs` and one `GET /openapi.json` route in `router.rs` (no new dependency: `serde_json` is already in the crate; `utoipa` needs no `swagger-ui` feature for raw JSON). Apply the same config gate as `/metrics` (`BOMA_METRICS`-style flag, default off) so a deployment does not advertise ops/internal paths by default, add the path to `web_fallback::deny_list`, and leave it unannotated so the contract test's generated ⊆ spec rule stays intact. Risks: (a) `/internal/health` is in the doc without `security`, so always-on serving could leak topology — gate first, then revisit with the owner; (b) the route itself is then an externally visible surface and needs a docs/PARITY.md entry if it becomes default-on; (c) the global `no-store`/timeout layers already cover it, do not add a second middleware stack; (d) worker 0105's "generate from served openapi.json" plan is blocked until this lands — sequence it before that codegen work.

2. **One metadata source; align tags.** Pull title/version/description into named constants in this module (or reuse `env!("CARGO_PKG_VERSION")` only after the contract-version question above is settled), fix the duplicate `ops` tag, and give the screen stream its own tag description consistent with `screen.rs`. Either align the generated `info` with `spec/openapi.yaml` or record the difference explicitly in `docs/STATE.md`. Risks: (a) aligning means editing the spec and refreshing `spec/EXPORT.md` provenance — owner approval, not a silent code change; (b) a new tag name absent from the spec is invisible to today's test but would fail a stricter future one, so update spec tags in the same change; (c) keep the RPC-exclusion paragraph in the description verbatim — clients rely on it.

3. **Make the coverage guard bidirectional and classify gaps.** Extend `crates/conformance/tests/contract.rs` with a second pass over spec paths: for each missing generated path, require an explicit allow-list entry marked "milestone gap" in `docs/STATE.md` (or a test-name-coded list in the test) keyed by path. Annotate the implemented-but-undocumented routes first — plugin-submissions, shared page, bot webhook, CSP report — reusing the spec's free-form `additionalProperties: true` request schemas and exact status sets (the `screen.rs:69` comment is the model). Risks: (a) a naive "spec == generated" assertion fails today on ~15 paths and would force fake annotations that lie about unimplemented behavior — hence the allow-list; (b) adding schemas can drift from the spec's own loose shapes, keep them deliberately permissive; (c) this is the largest slice — land the guard before the annotations so the gap is measured, not hidden; (d) generated-Schema field comparison must stay structural (contract.rs already ignores property order).

4. **Cache the document for serving.** Keep `document()` as the tested API, but add a `OnceLock<Vec<u8>>` (or `OnceLock<OpenApiDocument>`) used by the new handler so repeated `GET /openapi.json` calls do not rebuild the document. Risks: (a) safe only while the doc is compile-time static — any runtime/config-dependent `info` would make the cache stale, so proposal 2 must not introduce runtime version injection without invalidating it; (b) do not change `document()`'s signature until the conformance crate is updated in the same commit; (c) measured benefit is small — verify with a cheap benchmark before claiming a win; (d) keep `no-store` so clients cannot cache a stale copy.

5. **Prepare the ADR-003 codegen handoff without documenting RPC bodies.** Expose a machine-readable inventory of procedures (e.g. an `x-rpc-*` extension) derived from the `rpc.rs` registry at build time, so worker 0105 can generate URL/procedure constants from the same served document while this module's 5 HTTP paths stay as they are. Risks: (a) feasibility of utoipa extension/modifier syntax is GUESS — check docs.rs before committing; (b) the inventory must come from the registry, not a hand-written list, or it reintroduces the exact `runsRetry` drift 0105 found; (c) keep procedure request/response bodies in `03-api-contract.md` — one free-form body per procedure adds no client value; (d) coordinate the extension key names with 0105 so both sides agree.

## Non-goals and verification

No new HTTP behavior beyond the gated doc route, no RPC path in this document, no spec edit without owner sign-off, no second schema library, no Swagger UI bundle.
