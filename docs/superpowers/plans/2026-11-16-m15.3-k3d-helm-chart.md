# M15.3 — k3d single-node Helm chart implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Follow project rules in `AGENTS.md`: nothing edits before the task's file is named, every check runs, no claim without output.

**Goal:** A one-command, single-node Kubernetes deployment of Boma Bot on local k3d — app, worker, migrations, database — that boots the whole stack from a chart, with no requirement of external Postgres or an ingress controller.

**Architecture:** A plain Helm chart (`deploy/helm/boma-bot`) with four workload templates: a Postgres `StatefulSet`, a `migrate` `Job` (helm hook), an `app` `Deployment`, and a `worker` `Deployment`. One `Service` for the app. `ConfigMap` for the non-secret environment, `Secret` for `BOMA_MASTER_KEY` (required) and optionally the Postgres password (generated, then *read back* in k3d documentation). No TLS opinion: the docs say to put Caddy/Traefik/ingress-nginx in front for real TLS.

**Spec:** `docs/superpowers/specs/2026-11-15-m15-push-notifications-design.md` (M15.3 section), plus `docs/UPGRADING.md` (which this section extends), plus the runtime shape the compose stack proves:
`db → migrate → serve → worker`.

**Global Constraints:**
- Migrations referenced by the chart are the ones that ship in this release (comment in the migrator unit documents the count; today 58 migrations).
- The chart must render end-to-end with `helm template` and pass `helm lint` — CI enforces both.
- In-cluster Postgres is single-pod, sufficient only for k3d-class local bring-up. The README say so plainly; production must bring its own Postgres.
- No k3s features (server-side apply, PodSecurityPolicy, webhooks). Stock Helm + stock k3d only.
- `BOMA_MASTER_KEY` is *required* by the chart; omitting it is an install error with a legible message, never a degraded mode silent-boot.
- Nothing secret ever lives in `values.yaml` — the chart creates no default secrets, never prints one after creation, and never logs one.
- The web bundle is served by the same Go/Rust binary image as serve; `static export` is `COPY`ed at build time (mirrors the Dockerfile).
- Trace: `trace_check.py --max-missing 9` must stay at 3. No new product tests are added or removed by this milestone (docs + chart only).

**Review Focus:**
1. The chart must boot a real functional app — not `serve` without `worker`, not a migrate that fails silently leaving the app up half-migrated.
2. `BOMA_MASTER_KEY` shape: `Secret` with one key, `envFrom` into both workloads. One key, one meaning; don't split it across values files.
3. Helm hook ordering: `migrate` must run *before* `app` pods become Ready; app and worker must not touch Postgres before migration finishes.
4. Image reference must be a real pullable ref; `latest` or a made-up tag must never default in (`release tag` from values, documented).
5. Documented: where the chart boundary is (single-node, no HA, no webhooks), where it is not (with a real ingress/Traefik), and a copy-pasteable path to a local k3d cluster.

## Execution notes

- The `migrate` hook uses `helm.sh/hook: pre-install,pre-upgrade` and `helm.sh/hook-delete-policy: hook-succeeded` (matches `compose` semantics).
- The `worker` `Deployment` is the queue drain — `serve` alone never runs a run; the doc calls this out, as it does for compose.
- The chart never writes any real image tag into `values.yaml` — k3d docs say which one to pass and why; CI `helm template` runs with a fake tag to prove the shape, not the image.
