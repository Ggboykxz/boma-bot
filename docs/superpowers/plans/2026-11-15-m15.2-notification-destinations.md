# M15.2 — Slack/Teams notification destinations implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (or subagent-driven-development if the owner picks it) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Follow project rules in `AGENTS.md`: TDD, migrations never edited, REQ id in the test name, fmt + clippy `-D warnings` + workspace tests + `trace --max-missing 9` before every push.

**Goal:** A space can point Slack and/or Teams incoming webhooks at it so the same pushes that reach a member's browser also reach a shared channel, behind the same member policy + per-(space, user, bot) daily cap.

**Architecture:** A space-scoped `notification_destinations` table sealed under the space's data-encryption key (the vault's existing DEK flow); a `NotificationDestinationStore` port (PG + in-memory double); policy rows gain `destination_slack_webhook` / `destination_teams_webhook`; the push delivery path fires once per enabled destination kind after the browser sends, counts destinations against the **same** UTC-day cap as browser sends, and never propagates failure into a run.

**Tech Stack:** Rust (Tokio, sqlx PG, RLS), axum RPC, Next.js 15 static export (existing thread-header panel), Playwright.

**Spec:** `docs/superpowers/specs/2026-11-15-m15-push-notifications-design.md` (M15.2 section; decisions fixed: member-gated destination creation/deletion to Owner/Admin; policy gate = the initiator's own row + cap).

## Global Constraints

- REQ-065 (new, MUST) is the spec floor; the test budget stays `--max-missing 9` (two expected missing: REQ-049, REQ-056; REQ-061 counts too — three).
- Migrations are additive only. `0057_notification_destinations.sql` and `0058_notification_destination_flags.sql` only.
- New tables carry the tenant RLS idiom (`boma.current_space_id() OR boma.is_system()`, `FORCE ROW LEVEL SECURITY`).
- Destination webhook URLs are sealed in the vault (space DEK); RPC replies never carry them.
- Push delivery stays best-effort: any failing destination POST is logged and swallowed, never propagates into a run or any other code path.
- Cap is shared: browser sends + destination sends both count toward the same per(member, bot) UTC-day cap.
- Payload for destinations is title + one line of context; never message text, never tool names, never member names.
- Destination creation/deletion is Owner/Admin-only (existing `SPACE_ADMINS` + `require_space_role` in `usecases`).

## Review Focus

1. **Tenant scoping** — the destination store must never leak a row (or its ciphertext) to another space; the PG migration must be probed cross-tenant like M15.1's store was. (Task 4 pins this with `req_065_a_foreign_tenant_cannot_see_another_spaces_destinations`.)
2. **Webhook secret never travels** — RPC replies carry label + kind + createdAt only; ciphertext/nonce never leave the adapter. (Task 5 pins this with `req_065_destinations_list_returns_only_labels`.)
3. **Destination sends consume the shared cap** — browser + destination sends count together, a destination POST at the cap boundary is skipped just like a browser POST. (Task 5 pins this with `req_065_destinations_consume_the_shared_daily_cap`.)
4. **Best-effort at the seam** — a dead/slow slack endpoint POSTs and fails; the run's parked card remains answerable; no error surfaces to the caller. (Task 5 pins this with `req_065_a_wedged_destination_never_fails_delivery`.)
5. **Kind/payload correctness** — Slack gets `{text: ...}`; Teams gets a MessageCard; secret URL is never logged or reachable via any RPC reply. (Task 5 pins this with `req_065_destination_payloads_carry_only_titles_and_channels`.)

### REQ-065 — Notification destinations (MUST)
A space can name one or more Slack/Teams incoming webhooks; opted-in initiators receive pushes
there, alongside the browser, behind the same per-(space, member, bot) policy and daily cap.
Destinations are space-scoped, sealed at rest, and managed by Owners and Admins only.

  the member's kind for this bot, then the destination receives the same content-free text the
  browser would; nothing of the conversation travels.
- Given a destination that refuses or times out, the run is unaffected; the failure is logged.
- Rationale: teams live in Slack/Teams; the walk-away case is real and shared.

**Migration body (additive; no prior file is touched):**

```sql
-- REQ-065 (improvement program): space-scoped outgoing notification destinations, sealed like secrets.
CREATE TABLE notification_destinations (
    id            text PRIMARY KEY,
    space_id      text NOT NULL REFERENCES spaces (id) ON DELETE CASCADE,
    kind          text NOT NULL CHECK (kind IN ('slack_webhook', 'teams_webhook')),
    label         text NOT NULL,
    ciphertext    bytea NOT NULL,
    nonce         bytea NOT NULL,
    created_by    text NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT notification_destinations_label_not_empty
        CHECK (length(btrim(label)) > 0)
);
CREATE INDEX notification_destinations_by_space_kind
    ON notification_destinations (space_id, kind);
ALTER TABLE notification_destinations ENABLE ROW LEVEL SECURITY;
ALTER TABLE notification_destinations FORCE ROW LEVEL SECURITY;
CREATE POLICY notification_destinations_tenant ON notification_destinations
    FOR ALL
    USING (space_id = boma.current_space_id() OR boma.is_system())
    WITH CHECK (space_id = boma.current_space_id() OR boma.is_system());
```

### Task 5: delivery — destinations ride the push path

**Files:**
- Modify: `crates/app/src/push.rs` (delivery now fans out to destinations),
  `crates/app/src/usecases.rs` (none — usecases untouched),
  `crates/testkit/src/build.rs` (`ScriptedDestinationTransport`?), `crates/app/src/ports.rs` (port for destination transport — reuse `MessagingTransport` with `post_json(url, headers, body, allow_private)`)

**Implementation shape:**
- After the browser send loop in `push_one` (same policy, same cap), for each destination kind whose flag is enabled on the member's policy for this bot; the delivery fn obtains plaintexts **through** `destination_webhook(ctx, &id)` — it never reconstructs them from `ciphertext`/`nonce` in
  the app:
  - Read destinations of that kind at the space; rate-limited by the same `count_today` gate: number of sends in the UTC day including destinations must stay under `daily_cap`.
  - For each destination: decrypt through the store's internal helper (store hands plaintext only within the delivery fn — the store is the only sees plaintext), POST:
    - Slack: `{"text": "<title>"}` — the title is the same string the browser renders; one line, no links to conversations.
    - Teams: `{"@type":"MessageCard","@context":"http://schema.org/extensions","summary":"Boma Bot","title":"<title>","text":"","potentialAction":[{"@type":"OpenUri","name":"Open in Boma","targets":[{"os":"default","uri":"<app-base-url>/<bot-id>/"}]}]}`
  - On success: `record_send` (same log table, `kind` column gains `'destination'`, a separate migration adds the enum value... no — keep the log's `kind` CHECK unchanged by logging the destination carries the same kind as the underlying event (`waiting`/`completed`). The cap accounting keeps counting `kind` rows — destinations fall under the same kind as the event. Count them. That's exactly "shared cap".)
  - On failure: log `warn!`, never propagate.

**Default state:** `destination_slack_webhook` + `destination_teams_webhook` are false by default on the policy — opt-in per member.

**The payload for this case:** The notification delivers precisely the same title as the browser push, encoded appropriately per platform. NOTHING about the message, the bot's name, a link to another platform's message, an attachment summary, or any PII travels.

Required tests (all in `crates/testkit/src/build.rs`):
- `req_065_destination_sends_only_after_member_opts_in`
- `req_065_destination_payloads_carry_only_titles_and_channels` — assert exact JSON keys sent to the scripted transport; no message text, no bot name.
- `req_065_destinations_consume_the_shared_daily_cap` — create two browsers-capped + one destination; after cap reached, destination POSTs are skipped.
- `req_065_a_wedged_destination_never_fails_delivery` — transport returns 500; push_one returns Ok; the card answers in the room.
- `req_065_a_destinations_enabled_flags_are_independent_per_kind` — flag slack on, teams off → only slack receives.
- `req_065_destination_flag_off_means_never_send` — flags false for the member/bot pair → nothing leaves, not even for a configured destination.
