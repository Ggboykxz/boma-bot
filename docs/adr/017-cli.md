# ADR-017 — CLI and operator tooling: one binary with subcommands

Status: proposed (awaiting go)

## Context

Operators need migrate, bootstrap the first operator, rotate keys, export audit, run a health probe,
and inspect a stuck run. The spec treats these as operational, not product surfaces
(`04-nonfunctional.md`, REQ-053). The reference has `apps/api/src/cli/*` plus shell scripts.

## Alternatives

1. **One `boma` binary: `serve`, `worker`, `migrate`, `admin`, `probe`.**
2. Separate binaries per concern.
3. Shell scripts calling HTTP endpoints.

## Scoring

| Criterion | 1 subcommands | 2 many binaries | 3 scripts |
|---|---|---|---|
| 1 fits the spec | 1 | 1 | 3 (needs a running server, no bootstrap) |
| 5 simplicity | 1 | 3 | 2 |
| 3 security | 1 (one audited entry point, admin commands require local TTY) | 2 | 3 (shell quoting) |
| 6 typed contract | 1 | 1 | 4 |

## Decision

Option 1, with `clap`. `migrate` runs forward-only migrations under an advisory lock; `admin` requires
a local terminal or an explicit `--allow-remote` flag and writes to the audit log; `probe` exits
non-zero on a degraded dependency so a supervisor can act. No command reads a secret from argv
(environment or a prompt only).

## Consequences

- One artifact to build, sign and document; Compose uses the same image with different commands.
- Admin actions are auditable because they go through the same service layer as the API, not raw SQL.
- The CLI is the supported path for bootstrapping; the API never exposes "make me an operator".
